- 版本：`v0.1.2`
- 状态：已由本人签署；授权准备测试和采集有效红灯，不授权实现
- 形成日期：2026-09-19
- 课程编号：`codexfde`

## 1. 来源与目标

### 1.1 本人的真实问题

本人希望提高 AI 参与度，并明确跟踪每项需求从需求、设计、开发到验证的链路。原有过程无法判断需求的实现完整度或是否已完成测试。

### 1.2 V0.1 目标

- 保存项目、任务、任务创建时的需求／问题快照和多次运行记录。
- 让人能够重新查询需求边界、验收条件、设计／Spec、开发依据和验证材料。
- 对材料不完整的任务列出缺项和推荐澄清问题。
- 只报告已保存的事实与缺失证据，最终完整性和接受结论等待人工审核。
- 支持人按业务实现、约束条件、架构、部署、端到端验证和复用性等维度核对材料。

### 1.3 非目标

- 不自动调用 Codex，不提供完整执行器或网页。
- 不自动判断代码必然符合设计或 Spec。
- 不修改或开发 FlowERP；FlowERP 到 L04 才首次通过工作台开发。
- 不以“有成功记录”或“测试通过”代替人工验收。

网页 UI 是可比较的后续方案，不属于 L01 V0.1 交付范围。

推荐澄清遵循“目标方向建议 → 本人确认 → 包含／不包含边界清单 → 面向最终效果的验收条件”。目标建议不是本人决定，未确认时保持待澄清。

V0.1 的建议只来自固定、可解释的缺项模板：目标使用者与场景、期待的最终效果、包含／不包含范围、业务与技术约束、验收方式，以及架构、部署、端到端和复用性的适用性。已回答项目不重复追问。V0.1 不根据模糊描述自动生成业务目标方案；该能力留待后续 AI 协作阶段。

缺项按风险排序，验收条件位于首位。本人理由是：没有验收条件就无法判断结果是否正确。缺少验收条件时不得报告为可验证或可接受。

缺少验收条件时仍可保存澄清和设计探索记录，但不得通过 Spec 审核、进入开发或报告为可验证、完成或已接受。

## 2. 使用过程与对象

固定对象关系为：一个已登记项目可以有多项任务；一项任务保存创建时的需求／问题快照，并可追加多次运行记录。任务不能属于未登记项目，运行记录不能脱离任务。

本人确认的过程链路为：

需求录入（可能不完整） → 明确需求边界与验收条件 → 形成设计与 Spec → 基于 Spec 开发 → 核对代码是否符合 Spec／设计 → 核对是否守住原始边界并完成验收。

V0.1 用任务快照和多次运行记录保存这条链路。

不改变既定需求边界和验收条件的补充，作为原任务的新记录；改变需求边界或验收条件时，必须创建新任务编号并记录承接自哪个旧任务。旧任务不得被覆盖。

新增子需求和修改也使用独立任务编号，通过“子需求”或“修改自”关系连接原任务。每个节点分别保留自己的需求快照、Spec、开发和验证记录。

属于原任务已承诺范围的“子需求”未完成时，原任务不能进入最终接受；“修改自”任务独立验收，只在原任务链路中显示关系，不倒推改写或撤销原任务当时的结论。

任务创建时保存初始需求／问题快照。后续记录阶段固定为：`clarification`、`design`、`design_review`、`spec`、`spec_review`、`red`、`diff`、`green`、`final_review`；课程采集工具的 `observation` 只表示状态观察。所有记录至少保存所属任务、阶段、实际材料快照、来源或命令、结果和观察时间；审核记录另存审核对象、具名审核人、决定、理由和审核时间。失败或退回记录不得覆盖。

设计审核、Spec 审核均须在开发前通过；最终审核在验证证据形成后决定接受或退回。无需架构改动的小任务仍须记录“沿用现有架构”及理由。尚无最终审核记录时，即使材料完整，状态也保持 `pending_human_review`。

## 3. 五个 CLI 操作

五个操作通过现有 `python -X utf8 -m workbench.cli` 骨架接入。公共输出至少包含 `schema_version`、`ok` 和 `operation`；失败另含稳定 `error_code`、`message` 和适用的 `missing_items`。所有写操作仅在完整成功后提交。

| 操作 | 输入与正常结果 | 持久保存要求 | 错误与失败后状态 |
|---|---|---|---|
| `workbench-init` | `--runtime-dir --name --owner`；返回工作台身份与数据库位置 | 工作台名称、所有者和身份跨进程可重查 | 输入错误或初始化失败不得留下部分数据库状态 |
| `workbench-project-add` | `--runtime-dir --project-id --name --path --purpose`；返回项目对象 | 稳定编号、名称、规范化代码路径和用途 | 非法路径或重复编号必须拒绝，原项目不变 |
| `workbench-task-create` | 必填 `--runtime-dir --project-id --task-id --requirement-id --request --actor`；`--spec-file --problem-file` 可选；关联任务使用可选 `--related-task-id --relation`，关系为 `child_requirement` 或 `change_of` | 保存初始描述及当时提供的 Spec／问题全文快照和摘要；关系可重查 | 项目／关联任务不存在、关系跨项目或任务编号重复时拒绝；原对象不变。缺少可选材料时允许创建但列入缺项 |
| `workbench-evidence-add` | `--runtime-dir --task-id --phase --command-text --output-file --returncode --observed-at`；审核阶段另要求 `--reviewer --decision --review-note` | 输出文件内容按追加时快照保存；记录严格追加，阶段、命令、结果、时间和审核信息不覆盖 | 任务不存在、材料不可读、阶段字段不全或审核门闩顺序错误时拒绝，不留下孤立或半条记录 |
| `workbench-status` | `--runtime-dir`，可选 `--require-project --require-task --require-red-green-evidence`；返回对象归属、快照、记录、关联、`missing_items`、`clarification_questions`、`evidence_complete`、`acceptance` 和 `flowerp_connected` | 只读；同一数据库跨进程得到同一持久状态 | 缺失对象或必需证据返回稳定错误码和退出码 1；随后查询正确对象仍正常 |

`workbench-evidence-add --phase` 接受 `clarification`、`design`、`design_review`、`spec`、`spec_review`、`red`、`diff`、`green`、`final_review` 和课程工具使用的 `observation`。审核阶段的 `decision` 为 `approve` 或 `reject`。非审核记录不伪造审核字段。

`workbench-status` 中 L01 固定 `flowerp_connected: false`。没有最终具名审核时 `acceptance: pending_human_review`；拒绝决定和失败记录必须保留，后续通过不得覆盖。

### 3.1 结构化澄清、设计与 Spec 材料

`clarification`、`design`、`spec` 三类记录的 `--output-file` 必须是 UTF-8 JSON，顶层结构如下。澄清和设计阶段允许缺项；状态查询据实际缺项生成 `missing_items` 和 `clarification_questions`，不能替本人补值。

```json
{
  "schema_version": "1.0",
  "goal": "期待解决的最终问题或效果",
  "in_scope": ["明确包含的内容"],
  "out_of_scope": ["明确不包含的内容"],
  "acceptance_criteria": [
    {
      "id": "AC-EXAMPLE",
      "expected_effect": "面向最终效果的可观察结果",
      "verification": "怎样观察或复验"
    }
  ],
  "business_constraints": ["默认不得破坏的业务约束"],
  "technical_constraints": ["默认不得破坏的技术约束"],
  "architecture": {
    "applicability": "required | covered_by_existing | not_applicable",
    "decision": "采用或沿用的架构决定",
    "reason": "适用性与决定理由"
  },
  "deployment": {
    "applicability": "required | covered_by_existing | not_applicable",
    "approach": "新增方式或依赖的既有部署路径",
    "reason": "适用性理由"
  },
  "end_to_end": {
    "applicability": "required | covered_by_existing | not_applicable",
    "expected_effect": "需要保持或验证的端到端效果",
    "reason": "适用性理由"
  },
  "reuse": {
    "applicability": "required | covered_by_existing | not_applicable",
    "approach": "复用目标、既有能力或不适用说明",
    "reason": "评估理由"
  }
}
```

完整性规则：

- JSON 无法解析或 `schema_version` 不支持时，追加请求失败且不留下半条记录。
- `clarification`、`design` 可保存部分字段；空白或缺失字段继续列入缺项。
- `spec` 通过审核前，必须存在非空 `goal`，键 `in_scope`、`out_of_scope`，至少一条含 `id`、`expected_effect`、`verification` 的验收条件，以及 `business_constraints`、`technical_constraints` 两个键。
- `architecture`、`deployment`、`end_to_end`、`reuse` 必须分别给出上述三种 `applicability` 之一和非空 `reason`。`required` 时相应决定、路径或期待效果不得为空；`covered_by_existing` 时必须指出沿用内容；`not_applicable` 时理由不得为空。
- 验收条件是最高风险缺项；缺少时允许继续追加澄清和设计记录，但 `spec_review` 的 `approve` 请求必须失败，且不得进入开发阶段。
- 状态查询只依据保存的结构化快照和具名审核记录判断材料完整性，不从自然语言猜测字段，也不把模板建议当作本人答案。

关系为 `change_of` 的任务还必须在 `spec` 材料中提供：

```json
{
  "change_control": {
    "changed_constraints": ["被改变的约束"],
    "impact_scope": ["受影响范围"],
    "alternative": "替代方案及取舍",
    "migration_or_recovery": "迁移或恢复办法",
    "new_acceptance_criteria": ["新的验收条件编号"]
  }
}
```

上述五项均须非空；任一缺失时列入 `missing_items`，`spec_review` 的 `approve` 请求必须失败，并且任务不得进入开发。普通任务和 `child_requirement` 任务不强制该对象。

## 4. 固定失败语义

- 所有正常结果输出 JSON：`ok: true`，退出码为 0，并返回相关对象。
- 请求可解析但业务对象、关联或材料完整性不满足时输出 JSON：`ok: false`、稳定 `error_code` 和缺项，退出码为 1。
- CLI 参数格式错误退出码为 2。
- 重复任务编号不能覆盖旧任务内容或记录。
- 需求和输出保留创建／追加当时的快照。
- 错误请求不能破坏原记录，也不能留下无归属对象或半条数据。
- 材料不完整时列出缺失证据和推荐追问，但保留已有材料。
- 材料完整或测试通过仍只表示存在相应证据，状态必须等待人工审核。

## 5. 验收项

以下编号保持稳定；细节随访谈补齐，不预填实际结果。

### AC-01｜初始化和跨进程重查

- 前提：独立运行目录尚未初始化。
- 操作：初始化后结束进程，再用新进程查询。
- 预期响应：能读回同一工作台身份。
- 操作后数据：独立工作台数据库存在且内容未因进程结束丢失。

### AC-02｜项目、任务和记录的归属

- 前提：工作台已初始化并登记项目。
- 操作：在该项目下创建任务，再追加两次不同运行记录并查询。
- 预期响应：任务属于指定项目，两次记录均属于该任务且顺序可辨。
- 操作后数据：项目、任务和两次记录均保留；不得出现孤立记录。

### AC-03｜创建时快照不随原文件改变

- 前提：需求文件包含版本 A。
- 操作：创建任务后将原文件改为版本 B，再查询任务。
- 预期响应：查询仍返回创建时的版本 A 快照。
- 操作后数据：旧任务快照不被版本 B 覆盖。

### AC-04｜不完整材料、缺项和建议追问

- 前提：任务只保存了初始需求，尚无明确边界、验收条件或设计／Spec 证据。
- 操作：查询该任务状态。
- 预期响应：如实列出已有材料、缺项和针对缺项的推荐问题；不得报告为可开发、完成或已验收。
- 操作后数据：查询不改写任务，也不把建议当成本人回答。

### AC-05｜材料齐全仍等待人工审核

- 前提：任务已有需求边界、验收条件、设计／Spec、开发和测试记录。
- 操作：查询任务状态。
- 预期响应：返回材料及记录，但不自动给出最终接受结论。
- 操作后数据：审核状态保持待人工确认。

### AC-06｜重复任务编号保护

- 前提：任务编号已存在，且已有快照和运行记录。
- 操作：用同一编号提交不同内容，再查询原任务。
- 预期响应：第二次创建被拒绝。
- 操作后数据：原快照、记录、归属和任务总数均不变。

### AC-07｜错误追加不破坏旧数据

- 前提：已有正常任务及记录。
- 操作：向不存在的任务追加记录，再查询正常任务。
- 预期响应：错误追加被拒绝，正常任务仍可查询。
- 操作后数据：没有孤立记录，原任务内容与记录数不变。

### AC-08｜测试记录的结论边界

- 前提：任务有一条测试通过记录，但尚无具名人工审核。
- 操作：查询任务状态。
- 预期响应：能够确认“这次记录中的测试结果为通过”，但不能据此声称全部需求已实现或已经验收。
- 操作后数据：测试记录保留，审核状态不被自动改写。

本人确认：架构、部署、可扩展性、需求覆盖和未执行路径均不由单条绿灯记录证明，须另有证据并由人核对。

业务实现、需求约束和明确验收条件是每项任务的必查项。部署与复用性在需求分析或设计阶段标明“适用”或“不适用”；适用时列出条件与证据，不适用时写明理由。空白视为缺项，不得自动解释为不适用。

业务与技术约束默认不得破坏。架构默认进行影响评估，结论可以是不改变现有架构。复用现有部署方式时记录依赖路径；引入新部署方式时补充部署验证。局部算法变更不要求改变整体端到端体验，但不能破坏适用的端到端效果。复用性不是强制目标，但必须评估是否适用。

有意改变既有业务或技术约束时，必须创建独立“修改自”任务，写明被改变约束、影响范围、替代方案、迁移或恢复办法和新的验收条件；具名人工批准前不得进入开发。

### AC-09｜错误查询及恢复

- 前提：已有可查询任务。
- 操作：先查询不存在的任务，再用同一命令和观察顺序查询已有任务。
- 预期响应：第一次明确报错，第二次正常返回已有任务。
- 操作后数据：错误查询不创建或修改任何记录。

### AC-10｜失败记录如实保留

- 前提：同一任务先后产生失败和通过记录。
- 操作：按同一查询方式查看该任务。
- 预期响应：两次实际结果均可见，失败没有被通过记录覆盖或伪装。
- 操作后数据：历史记录分别保存并能辨别先后。

### AC-11｜改变边界时建立承接任务

- 前提：原任务已有明确需求边界和验收条件。
- 操作：提出会改变边界或验收条件的后续需求。
- 预期响应：不能用原任务编号覆盖创建；使用新编号创建时，可查到它承接的原任务编号。
- 操作后数据：原任务保持不变，新旧任务分别存在且关联可追溯。

### AC-12｜子需求或修改节点可追溯

- 前提：原任务已存在，并出现新的子需求或改变原边界／验收的修改。
- 操作：使用新任务编号创建相应节点，再查询原任务及新任务。
- 预期响应：能辨别该节点是原任务的“子需求”还是“修改自”关系；每个节点分别显示自己的快照和记录。
- 操作后数据：原任务未被覆盖，新节点归属于同一已登记项目且关联可查。

### AC-13｜关联节点影响完成度但不改写历史

- 前提：原任务分别关联一个未完成的必需子需求和一个后续修改任务。
- 操作：查询原任务的材料完整性和接受状态。
- 预期响应：未完成子需求阻止原任务最终接受；后续修改单独显示和验收，不撤销原任务在原边界内的历史结论。
- 操作后数据：三个任务及其各自快照、记录和关系均保持不变。

### AC-14｜适用性判断与空白缺项

- 前提：任务已给出业务和验收条件，但部署或复用性字段为空。
- 操作：查询任务材料完整性。
- 预期响应：空白被报告为待澄清；明确标为不适用且有理由时，不再作为该维度缺项。
- 操作后数据：查询不替本人填写适用性，也不自动生成理由。

### AC-15｜建议目标与最终效果验收

- 前提：初始输入没有明确目标、包含／不包含边界或最终效果。
- 操作：查询任务缺项，再追加本人确认的澄清记录并重新查询。
- 预期响应：首次查询给出建议目标和缺项，但保持待澄清；再次查询能区分已确认目标、边界和面向最终效果的验收条件。
- 操作后数据：建议内容不被冒充为本人决定；初始快照和后续确认记录均保留。

### AC-16｜改变既有约束必须先批准

- 前提：原任务已有明确业务或技术约束，新请求有意改变其中一项。
- 操作：建立“修改自”任务但不提供完整影响说明或人工批准，再查询其可开发状态。
- 预期响应：列出缺少的影响、替代方案、迁移／恢复、新验收或批准材料，并拒绝报告为可开发。
- 操作后数据：原任务保持不变，修改任务保持待澄清或待批准；不得产生开发完成记录。

### AC-17｜分阶段具名审核关口

- 前提：任务已有设计和 Spec 材料，但尚无相应具名审核决定。
- 操作：查询可开发状态；随后追加设计与 Spec 审核决定，再次查询；验证后未追加最终审核时再查询接受状态。
- 预期响应：首次不得报告为可开发；中间查询可报告审核材料已具备但不代表最终接受；最后仍为 `pending_human_review`，直到具名最终审核完成。
- 操作后数据：每次审核分别保存审核对象、审核人、决定、理由和时间，早期审核不得被最终审核覆盖。

### AC-18｜缺少验收条件时不得误报

- 前提：任务已有目标、边界或设计材料，但没有明确验收条件。
- 操作：查询缺项、可验证状态和接受状态。
- 预期响应：验收条件作为首要缺项；不得报告为可验证、完成或已接受，并给出面向最终效果的澄清提示。
- 操作后数据：已有材料保持不变，查询不替本人生成或确认验收条件。

### AC-19｜结构化材料驱动缺项且不猜测自然语言

- 前提：同一任务先追加一份缺少验收条件的合法部分 JSON，再准备一份字段齐全的 Spec JSON。
- 操作：第一次查询缺项；尝试批准不完整 Spec；随后追加完整 Spec 并再次查询。
- 预期响应：首次将验收条件列为首要缺项，批准请求被拒绝；完整 Spec 保存后，已提供字段不再重复追问，但仍须经过具名 Spec 审核。
- 操作后数据：两次材料快照分别保留；被拒绝的批准不产生通过记录，模板建议不写回本人材料。
